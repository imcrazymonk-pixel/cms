# ADR-003: Прокси и настройки интеграций

## Status

Accepted

## Date

2026-11-15

## Context

CMS ходит наружу в четыре HTTP-сервиса: Bedolaga Bot Web API, Telegram Bot API
(Саппорт), Platega и YooKassa. Отдельно читает PostgreSQL бота (тарифы) по TCP.
До этого решения:

- настройки интеграций жили только в ENV, UI для них не было;
- прокси не поддерживался вообще, httpx неявно уважал `HTTP_PROXY`/`HTTPS_PROXY`;
- нельзя было пустить один сервис через прокси, а другой напрямую;
- проверить подключение без сохранения и рестарта было невозможно.

Bedolaga DB — это прямой TCP-коннект через socat-мост; HTTP-прокси к нему неприменим.

## Decision

1. **Единый реестр настроек.** Все параметры интеграций — ключи `settings_registry.py`
   с `tab="integrations"` и `store="settings"` (БД → env → default). Секреты шифруются AES.
   Существующие Platega/YooKassa credentials остаются в `fin_settings` (env-first).
2. **Модель прокси.** Глобальный прокси по умолчанию (`outbound_proxy_*`) плюс у каждой
   HTTP-интеграции режим `inherit | direct | custom` и собственные URL/исключения.
3. **Протоколы.** `http`, `https`, `socks5`, `socks5h`; логин/пароль в URL.
   Для SOCKS нужен `socksio` (`httpx[socks]`); без пакета socks-URL не сохраняется.
4. **`no_proxy`.** Хосты и суффиксы (`.example.com`), `*` — без CIDR. Сравнение по hostname.
5. **`trust_env=False`.** Все клиенты интеграций создаются с этим флагом: режим `direct`
   обязан быть действительно прямым, а не «прямым через HTTP_PROXY из окружения».
6. **Применение без рестарта.** Сохранение настроек вызывает `on_settings_changed`:
   пересоздаёт клиент Bedolaga, переподключает Bedolaga DB и делает in-place reload Саппорта.
   Ошибка применения не отменяет сохранение — попадает в `runtime.warnings`.
7. **Reload Саппорта in-place.** `SupportService`, `store`, `outbox`, `event_bus`
   переиспользуются, чтобы не рвать живые WebSocket-подписки. Порядок:
   stop workers → close TG clients → unregister senders → clear pollers → wire → start.
8. **Bedolaga DB в UI без прокси.** Host/port/БД/логин/пароль редактируются, но
   proxy-полей нет; в интерфейсе подпись про SSH-туннель/VPN.

## Consequences

Плюсы:

- одна точка управления всеми исходящими подключениями;
- можно проверить подключение и увидеть внешний IP до сохранения;
- предсказуемое поведение: прокси только там, где он явно задан;
- настройки применяются без рестарта контейнера.

Минусы / долг:

- reload Telegram-поллера на секунду останавливает приём сообщений;
- `no_proxy` не поддерживает CIDR;
- очистить сохранённый секрет пустым полем нельзя — только сбросом ключа или режимом `direct`;
- SOCKS добавляет зависимость `socksio`;
- при падении `init_support` rollback восстанавливает каналы, но это редкая ветка без
  полноценного интеграционного теста.

## Alternatives

- **Только ENV.** Отклонено: нет UI, проверки и применения без рестарта.
- **Прокси параметром на каждый запрос.** Отклонено: клиенты кэшируются, настройки должны
  применяться один раз при сохранении, а не перечитываться на каждом вызове.
- **Отдельная таблица `integration_settings`.** Отклонено: реестр уже даёт типы, секреты,
  источники и UI; новая таблица дублировала бы механизм.
- **Прокси для Bedolaga DB через SOCKS-туннель.** Отклонено: asyncpg не умеет HTTP-прокси,
  а туннель — инфраструктурная задача, не настройка CMS.
