## 1. Цель (простыми словами)

В админке CMS появляется группа **«Саппорт»** (раскрывающееся меню, как
«Bedolaga Bot») с 7 экранами. Операторы **отвечают клиентам из браузера** в
дизайне Remnawave. Настройки поддержки — вкладкой в «Настройках CMS».
ИИ-помощник предлагает ответы (шлёт человек), учится на реально отвеченных
диалогах и подпитывается базой знаний. Живой Telegram-бот поддержки пока
работает параллельно, позже его функции вливаются в единую систему.

**Ключевое решение владельца (2026-10-23):**
ai-support **переписывается и внедряется в CMS полноценно** — единый код на
стеке CMS (FastAPI + PostgreSQL + React/Remnawave-дизайн). **НЕ прокси и НЕ
костыль.** Внешний Node-сервис ai-support после переноса больше не нужен.

## 2. Карта компонентов

| Компонент | Где | Статус после переноса |
|---|---|---|
| **CMS** | `web/frontend` (React, Remnawave) + `web/backend` (FastAPI) | Здесь живёт всё: и админка, и «Саппорт» |
| **Прокси Bedolaga** | `web/backend/api/v1/bedolaga/*` | Останется (источник данных о клиентах/тикетах) |
| **ai-support (Node)** | `NewWeb/ai-support` (эталон) | **Источник кода для переноса.** Потом — только референс |
| **Бот поддержки (форум-мост)** | `NewWeb/bot` (grammY, Node) | Сейчас живой. После переноса — кандидат на отключение |
| **Bedolaga Bot Web API** | внешний | Остаётся (тикеты/клиенты) |
| **Remnawave** | `panel.fortf.ru` | Остаётся (данные клиента: подписка/устройства) |

Целевая архитектура (единый процесс CMS):

```
[Браузер: /admin/support/*  (React, Remnawave-стиль, вход JWT админа)]
        │ WebSocket для живых обновлений
        ▼
[FastAPI backend (web/backend)]  ← фоновые задачи (поллеры, SLA, уведомления)
        │
        ├── Bedolaga Bot Web API (тикеты, клиенты) — HTTP
        ├── Telegram (личка клиентов; позже — форум-мост) — Bot API
        ├── Remnawave (карточка клиента) — HTTP
        ├── ИИ-провайдер (OpenAI-совместимый) — HTTP
        └── PostgreSQL (очередь, сообщения, КБ, SLA, операторы, аудит, медиа)
```

**Последствие (важно понимать):** раз мы берём код ai-support как основу и
пишем его заново в стеке CMS — апдейты от автора ai-support к нам больше не
приходят (лицензия MIT это позволяет, форк законен). Всю поддержку берём на
себя. Это осознанный выбор владельца.

## 4. План переноса (миграция модулей ai-support → CMS)

### 4.1. Куда переносим что (карта модулей)

| Модуль ai-support (Node) | Порт в CMS | Куда |
|---|---|---|
| `core/db.ts` (19 миграций SQLite) | PostgreSQL-миграции (наш `db/postgres/migrations/`) | `db/postgres/migrations/` |
| `core/store.ts` (диалоги, сообщения, события, EventEmitter) | Pydantic+SQLAlchemy async; события — через asyncio pub/sub + WS | `web/backend/core/support/store.py` |
| `core/outbox.ts` (единый выход наружу, окно 24 ч) | аналог на Python (иммутабельный паттерн) | `web/backend/core/support/outbox.py` |
| `channels/bedolaga.ts` (поллер тикетов) | httpx-поллер (у нас уже есть `bedolaga_client.py`) | `web/backend/core/support/channels/bedolaga.py` |
| `channels/tgdm.ts` (Telegram личка/Business) | Python-библиотека Telegram (вопрос А3) + фоновый воркер | `web/backend/core/support/channels/telegram.py` |
| `integrations/remnawave.ts`, `customers.ts`, `bedolaga-customer.ts` | Python-клиенты (хелперы на httpx) | `web/backend/core/support/integrations/*.py` |
| `ai/*` (provider, gate, responder, kb, scrub, mining, cluster, sublink) | Python-модули (httpx, OpenAI-совместимый протокол) | `web/backend/core/support/ai/*.py` |
| `core/sla.ts`, `core/notify.ts`, `core/templates.ts`, `core/media.ts`, `core/nodes.ts` | Python-модули + фоновые asyncio-задачи | `web/backend/core/support/*.py` |
| `panel/server.ts` (Fastify API+WS) | FastAPI-роутеры `/api/v1/support/*` + WebSocket | `web/backend/api/v1/support/` |
| `public/index.html` (панель UI) | React-страницы в Remnawave-дизайне (shadcn) | `web/frontend/src/pages/support/*.tsx` |
| `kb/*.md` (база знаний) | PG-таблица + полнотекстовый поиск | `db/migrations` + UI |

### 4.2. Структура меню «Саппорт» (подтверждено)

1. **Очередь обращений** — список + переписка + статусы + черновик ИИ + карточка клиента (всё сразу)
2. **Контроль SLA**
3. **База знаний**
4. **ИИ-ассистент**
5. **Шаблоны ответов**
6. **Аналитика**
7. **Команда** (пока роли не вводим: все админы CMS = операторы, пункт оставляем как «аудит/присутствие»)

Плюс: карточка клиента тянет данные **Bedolaga + Remnawave** (дальше донастроим).

### 4.3. «Настройки CMS» → вкладка «Поддержка» (подтверждено)

- Подключение (статус, адреса), Каналы (переключатели в админке), ИИ (режим/модель/язык),
  Уведомления, SLA, шаблоны, медиа-лимиты.
- **Секреты: ключи и токены лежат в `.env` (закомментированные дефолты) и переопределяются
  из админки (хранятся в БД).** В UI редактируем, в git не светятся.

### 4.4. Фазы миграции (предлагаемый порядок — уточняется вопросами)

- **Фаза 0 — Каркас.** Миграции БД (диалоги, сообщения, операторы, КБ, SLA, аудит);
  каркас `core/support` (store/outbox/события); health. **Ничего не ломает.**
- **Фаза 1 — Bedolaga-канал + «Очередь».** Поллер тикетов, импорт, ответы из веба
  текстом, статусы, WS. **Первый живой результат: отвечаем клиентам из админки.**
- **Фаза 2 — Telegram-канал и интеграция форум-бота.** Приём лички, ответы файлами,
  живой WS; бот поддержки продолжает работать, его переписка видна в карточке (мост).
- **Фаза 3 — ИИ и база знаний.** Провайдер, черновики, ворота, КБ (создание/дообучение
  из отвеченных диалогов), ИИ-ассистент и экраны КБ.
- **Фаза 4 — SLA, шаблоны, уведомления, аналитика, команда/аудит.**
- **Фаза 5 — Полировка.** Медиа-лимиты, карточка клиента deep (Remnawave), вкладка
  «Поддержка» в настройках, удаление Node-сервиса (по согласованию).

Каждая фаза заканчивается рабочим деплоем на существующую инфраструктуру.
